# Как мы сделали свою видеосвязь и корпоративный мессенджер на Jitsi, Keycloak и Matrix

Эта статья про то, как из открытого docker-jitsi-meet и связки open source сервисов получилась внутренняя система видеоконференций с разделением прав по SSO, а потом рядом с ней вырос ещё и полноценный мессенджер с чатами, звонками и вложениями. Всё крутится на одном сервере без выхода в интернет, поэтому по пути пришлось решать не только прикладные, но и логистические задачи: как доставить статические бинарники Node.js и образы Docker туда, где нет ни GitHub, ни Docker Hub, ни npm.

Домены, IP адреса и название компании в статье и в репозитории заменены на условные (`example.ru`, `10.20.30.10`, `Компания`), внутренняя структура и логика решений сохранены без изменений.

## Постановка задачи

Заказчику нужен был сервис видеоконференций с простой и понятной для пользователей логикой:

* гость из интернета может присоединиться к уже идущей встрече по прямой ссылке `https://go.example.ru/<комната>`, но не может её создать;
* сотрудник из офиса может создавать конференции; для этого он один раз логинится через корпоративный Keycloak;
* если сотруднику прислали ссылку на чужую уже идущую встречу, он тоже проходит через Keycloak (для идентификации), но входит обычным участником, а не модератором;
* никаких отдельных «секретных» ссылок для входа сотрудников быть не должно, всё работает через один и тот же URL.

Стандартный docker-jitsi-meet такого поведения из коробки не даёт. Ближе всего к задаче подходит режим JWT авторизации (`ENABLE_AUTH=1`, `AUTH_TYPE=jwt`, `ENABLE_GUESTS=1`), но кто и как выдаёт этот JWT, нужно было придумать самим.

## Общая архитектура

Идея простая: перед тем как отдать пользователю страницу конференции, нужно понять, откуда он пришёл (из офиса или снаружи) и есть ли у него уже права на создание комнаты. Всю эту логику взял на себя nginx вместе с небольшим самописным сервисом.

Схема запроса для сотрудника из внутренней сети, который открывает `https://go.example.ru/1122` без токена в URL, выглядит так:

```
Браузер сотрудника (внутренняя сеть)
        │  GET https://go.example.ru/1122
        ▼
     nginx  (это внутренний IP и однословный путь? → 302 на /moderator/1122)
        │
        ▼
   /moderator/1122  (доступен только из частных подсетей)
        │
        ▼
   oauth2-proxy (127.0.0.1:4181)  →  auth_request к Keycloak компании
        │  (нет сессии → редирект на логин; сессия есть → сразу дальше)
        ▼
   jwt-minter (127.0.0.1:3301)  получает email/имя от oauth2-proxy,
        спрашивает у jicofo, идёт ли уже конференция "1122":
          не идёт → подписывает JWT с moderator=true (создатель)
          уже идёт → обычный участник без прав модератора
        │
        ▼
   302 на https://go.example.ru/1122?jwt=<токен>
        │
        ▼
   Jitsi Web  проверяет JWT через Prosody и jicofo
```

Гость из интернета в этой схеме вообще не касается Keycloak: он либо попадает в уже идущую конференцию через анонимный гостевой домен, либо, если пытается открыть несуществующую комнату, встаёт в стандартный для Jitsi режим ожидания модератора.

## Keycloak клиент и почему пришлось писать свой мост

У компании уже был настроен OIDC клиент `jitsi` в Keycloak, и он был confidential (то есть с секретом на стороне сервера, а не публичный PKCE клиент для браузера). Доступа к консоли Keycloak на изменение конфигурации клиента не было, поэтому переиспользовали то, что есть, вместо того чтобы просить завести новый клиент.

Готовые интеграции вроде `jitsi-keycloak` из открытых репозиториев рассчитаны как раз на публичный клиент: логин прямо в браузере, без секрета, через PKCE. Для confidential клиента обмен кодом авторизации на токен обязан идти через сервер, а не через JS в браузере. Поэтому родился отдельный маленький стек:

* **oauth2-proxy** берёт на себя весь OIDC handshake с Keycloak и держит сессию пользователя в cookie;
* **jwt-minter**, самописный сервис на Node.js без внешних зависимостей, получает от oauth2-proxy заголовки с личностью пользователя и сам решает, кому какие права выдавать, а затем подписывает JWT для Jitsi.

oauth2-proxy запускается как systemd сервис со `DynamicUser=true` (каждый раз новый случайный UID), слушает только `127.0.0.1:4181` и наружу не торчит вообще, доступ к нему регулируется на уровне nginx.

Отдельно стоит сказать про формат `cookie_secret`: он обязан быть в base64 в URL safe алфавите, ровно 32 байта до декодирования. Обычный `openssl rand -base64 32` даёт не тот алфавит, и сервис падает с ошибкой про длину секрета. Рабочий способ сгенерировать такой секрет:

```bash
python3 -c "import secrets, base64; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode())"
```

## nginx: кто и куда идёт

Вся маршрутизация построена на одной идее: определить IP клиента через `geo` директиву и на основе этого решить, нужен ли ему шлюз аутентификации.

```nginx
geo $is_internal {
    default 0;
    10.0.0.0/8 1;
    172.16.0.0/12 1;
    192.168.0.0/16 1;
}
```

Дальше в основном location блоке, который ловит однословные пути вида `/1122` или `/` (регулярка `^/([^/?&:'"]*)$`, то есть без слэшей внутри):

* если в запросе уже есть `?jwt=`, отдаём страницу как есть;
* если клиент внешний, тоже отдаём как есть, гостей не трогаем;
* иначе (внутренняя сеть, токена ещё нет) редиректим на `/moderator/<то же имя>`.

Отдельно вынесены точные (`=`) location блоки для статики вроде `config.js`, `interface_config.js`, `manifest.json`, `favicon.ico`, `http-bind`, `xmpp-websocket`: без этого они попадали бы под общую регулярку как «имя комнаты» и заворачивались бы на шлюз, что явно не то, что нужно.

`/moderator/` и `/oauth2/` закрыты по IP на уровне nginx: `allow` только для частных подсетей, `deny all` для остальных. Из интернета туда физически не достучаться, ответ 403.

При работе с большими OIDC токенами Keycloak nginx падал с `upstream sent too big header`: стандартных буферов не хватает под объёмные `Set-Cookie`. Лечится увеличением буферов:

```nginx
proxy_buffer_size 16k;
proxy_buffers 4 16k;
proxy_busy_buffers_size 32k;
```

## Флаги docker-jitsi-meet

Ключевые переменные, которые включают проверку токена и определяют поведение гостей:

```
JICOFO_ENABLE_REST=1
ENABLE_AUTH=1
AUTH_TYPE=jwt
ENABLE_GUESTS=1
JWT_APP_ID=jitsi
JWT_ACCEPTED_ISSUERS=jitsi
JWT_ACCEPTED_AUDIENCES=jitsi
```

`ENABLE_GUESTS=1` поднимает параллельно анонимный XMPP домен, через который гости без токена заходят в уже идущие конференции. `JICOFO_ENABLE_REST=1` отдельно от авторизации участников включает REST API у jicofo внутри контейнера: по умолчанию jicofo слушает `127.0.0.1` в собственном сетевом namespace, и снаружи контейнера это в принципе непробиваемо, даже с проброшенным портом в docker compose. Без этого флага jwt-minter не смог бы спрашивать, идёт ли уже конференция в конкретной комнате. Порт наружу при этом по прежнему не открыт, доступен только с самого сервера.

После правки `.env` контейнеры нужно именно пересоздать, обычный `restart` новый файл окружения не подхватывает:

```bash
sudo docker compose up -d --force-recreate prosody jicofo web jvb
```

## Права модератора: путь проб и ошибок

Здесь была самая долгая часть работы, потому что первый план оказался нерабочим.

### План А: claim в JWT (не сработал)

Изначальная идея была в том, чтобы jwt-minter подписывал токен с claim `context.user.moderator: true` или `false`, а модуль Prosody `mod_token_affiliation` на основе этого claim выставлял affiliation `owner` или `member`. Модуль работал правильно сам по себе (проверялось через `prosodyctl shell`), но результат постоянно перебивался: в этой сборке jicofo делает владельцем комнаты любого участника с валидным JWT для аутентифицированного домена, независимо от значения claim `moderator`. Официальный флаг `ENABLE_AUTO_OWNER=0` был выставлен и подтверждён в рендере конфига, но даже после полного `stop`/`up` контейнеров оба участника всё равно получали `role=moderator, aff=owner`, что проверялось многократно вживую во время реальных звонков. Разбираться дальше во внутренностях nightly сборки jicofo решили не тратить время, раз нашлась рабочая альтернатива.

### План Б: не модераторам JWT просто не выдаётся (сработал)

Единственный способ, который стабильно работает: гостевой вход без токена, тот же самый путь, которым и так заходят настоящие внешние гости. Он гарантированно не даёт прав владельца, потому что это тот же анонимный XMPP домен.

Логика jwt-minter в итоге стала такой:

* если по внутренней логике захвата комнаты (см. ниже) пользователь считается создателем, выдаётся обычный JWT с `moderator: true`;
* если пользователь не создатель, а комната уже идёт, JWT вообще не выдаётся. Вместо `?jwt=` в редиректе передаются `?guest_name=<ФИО>&guest_email=<email>`.

Фронтенд получает из финального URL либо `jwt`, либо `guest_name`/`guest_email`, и передаёт их в `JitsiMeetExternalAPI` через штатный параметр `userInfo`, который умеет предзаполнять имя гостя без всякого JWT. Так закрываются сразу оба требования: прав модератора у обычного участника нет, но имя всё равно отображается настоящее, а не случайный номер гостя.

### Гонка при одновременном создании комнаты

Отдельная проблема: jicofo узнаёт о том, что комната существует, только через мгновение после того, как в неё кто-то реально зашёл. Если два сотрудника кликали по одной и той же новой ссылке почти одновременно, оба успевали получить от jicofo ответ «комната ещё не существует» и оба получали права модератора.

Исправлено добавлением в jwt-minter лёгкого захвата комнаты в памяти процесса, без файлов и базы данных:

* если jicofo подтверждает, что комната реально идёт, модератором становится только тот, чей email совпадает с уже записанным создателем; остальные обычные участники;
* если по мнению jicofo комнаты ещё нет, модератором становится тот, кто попросил первым, и это фиксируется на 20 секунд, чего достаточно, чтобы перекрыть задержку регистрации в jicofo;
* как только все выходят и jicofo перестаёт числить комнату идущей, следующий, кто откроет комнату с тем же именем, снова становится её модератором.

### Собственный iframe попадал в свой же гейт

После перехода на схему без JWT для гостей всплыл ещё один баг. Портал встраивает конференцию через `<iframe src="https://go.example.ru/<room>">`. Без `jwt` в URL этот запрос ловил тот же самый regex гейт, который создавался для прямых переходов в браузере, и заворачивал iframe на `/moderator/`. Для сотрудника это означало логин в Keycloak внутри iframe, а Keycloak по собственной политике `frame-ancestors 'self'` отказывался открываться во встроенном фрейме: пустой экран вместо звонка.

Чинится проверкой заголовка `Sec-Fetch-Dest`, который современные браузеры сами проставляют в `iframe` для встроенных фреймов и в `document` для обычных переходов:

```nginx
location ~ ^/([^/?&:'"]*)$ {
    if ($arg_jwt) { break; }
    if ($http_sec_fetch_dest = "iframe") { break; }
    ...
}
```

## Брендинг интерфейса

Задача была убрать все упоминания Jitsi из интерфейса и оформить всё в цветах компании, не трогая при этом функциональность.

Docker jitsi meet даёт для этого сразу несколько независимых точек кастомизации:

1. **interfaceConfig** через файл `custom-interface_config.js`, который entrypoint веб контейнера сам дописывает в конец стандартного `interface_config.js`. Ключевая переменная `APP_NAME`: она подставляется в переводах вместо `{{app}}`, убирает фразы вроде «Спасибо, что используете Jitsi Meet» и «Сервер видеоконференцсвязи Jitsi» без правки самих файлов перевода, которые легко потерять при обновлении образа.
2. **Динамический брендинг** через `BRANDING_DATA_URL`, который отдаёт nginx напрямую с диска (`branding.json` с логотипом, цветом фона и палитрой кнопок).
3. **Статические файлы** (`title.html`, `manifest.json`, favicon), которые нельзя перекрыть через общий config маунт, потому что корневая файловая система веб контейнера доступна только для чтения. Пришлось добавить отдельные bind mount поверх штатных файлов образа в `docker-compose.yml`.
4. **head.html**, который инжектится через SSI в `<head>` страницы, для CSS правок, которые не покрываются `interfaceConfig`: размер логотипа на welcome странице, фон шапки, адаптив под мобильные экраны.

Отдельно был официальный, а не хакерский способ перекрасить кнопки целиком через MUI тему приложения, поле `customTheme.palette` в том же `branding.json`. Значения там это базовые токены темы, ключевой для основных кнопок токен `action01` вместе с его состояниями `hover01`, `active01`, `focus01`.

Из мелких, но показательных багов брендинга:

* футер с иконками App Store и Google Play не убирался через `interfaceConfig.MOBILE_APP_PROMO = false`, потому что этот флаг отвечает за другой сценарий (мобильный deep linking), а за постоянный футер на десктопе отвечает отдельный флаг `DISPLAY_WELCOME_FOOTER`;
* мобильный экран заглушка Jitsi «Video chat isn't available on mobile» блокировал именно тот сценарий, ради которого всё затевалось, гостя с телефона по ссылке. Отключается через `config.disableDeepLinking = true`;
* поле ввода названия конференции на welcome странице не проверяло кириллицу, из-за чего у собеседников название отображалось битым текстом, а иногда происходил отказ входа. Своего конфига валидации имени комнаты у Jitsi нет, поэтому фикс сделан прямо в `head.html` небольшим скриптом на встроенном браузерном `setCustomValidity`, без единой правки React кода Jitsi.

## Корпоративный мессенджер поверх той же SSO сессии

Позже к видеосвязи добавили ещё и полноценный мессенджер по пути `/app/`: чаты, контакты, звонки, профиль, в стиле привычных мобильных мессенджеров. Ключевое ограничение было прежним: никаких новых прав и клиентов в Keycloak не заводить, использовать ту же самую SSO сессию, что уже работает для видеозвонков.

### Почему Matrix

Matrix Synapse выбрали как self-hosted протокол для чатов без регистрации и без платных лицензий. Федерация с внешними серверами полностью выключена (`federation_domain_whitelist: []`), это закрытая система только для сотрудников компании. База данных Postgres, а не встроенный sqlite, `enable_registration: false`, обычной self-service регистрации нет.

### Мост между Keycloak сессией и Matrix сессией

`matrix-auth-bridge`, ещё один маленький Node сервис без npm зависимостей, стоит за тем же oauth2-proxy и читает те же заголовки с личностью пользователя, что и jwt-minter. При обращении фронтенда он:

1. достаёт ФИО пользователя из id токена Keycloak (не из access токена, как делалось раньше: там реального имени не было, только технический логин);
2. создаёт или обновляет пользователя в Synapse через Admin API, при создании с одноразовым случайным паролем, которым никто никогда не логинится;
3. выпускает свежий Matrix access token через админский эндпоинт логина от имени пользователя, без пароля и без настройки отдельного OIDC клиента внутри самого Matrix;
4. пишет пользователя в собственный плоский файл с ростером контактов.

Справочник контактов ведётся именно так, а не через встроенный поиск пользователей Synapse, по органическому принципу: список пополняется по факту первого входа сотрудника в портал. Полной выгрузки всех сотрудников компании из Keycloak нет, потому что для этого клиенту `jitsi` пришлось бы выдавать право `view-users`, а на такое решили не идти.

### Фронтенд: React, Vite, matrix-js-sdk

Портал собирается в отдельной песочнице с доступом в интернет (сам сервер без исходящего интернета), готовая сборка заливается на сервер архивом. По функциям это уже полноценный мессенджер:

* групповые и личные чаты с автоматическим приёмом приглашений;
* вложения (фото и файлы) через авторизованный медиа эндпоинт Synapse;
* редактирование и удаление сообщений через штатные механизмы Matrix (`m.replace` и redaction);
* реакции на сообщения стандартным эвентом `m.reaction`;
* голосовые сообщения через `MediaRecorder`;
* добавление и просмотр участников группового чата;
* опросы на собственных, не входящих в спеку Matrix типах событий (стандартная спека Matrix Polls показалась слишком громоздкой для внутреннего инструмента);
* ответы на сообщения с цитированием оригинала;
* упоминания через `@Имя`, тоже собственная конвенция без официального механизма Matrix Mentions;
* индикатор непрочитанных в списке чатов и разделительная полоса в самой ленте, как в привычных мессенджерах;
* поле «о себе» в профиле и карточки контактов.

### Несколько показательных багов на пути

* **Переписка сама с собой.** Личный чат создаётся через `createRoom` с приглашением второго участника, а он при этом попадает в статус invite, а не сразу join. Без автоматического приёма приглашения каждый видел только свою половину переписки: фактически две разные комнаты, потому что поиск существующего чата проверял только уже принятых участников.
* **Аватар не менялся.** Актуальные версии Synapse отдают медиа только по авторизованному эндпоинту с Bearer токеном, обычная ссылка картинка без токена получает отказ молча, без видимой ошибки в интерфейсе. Исправлено загрузкой через `fetch` с токеном и локальной blob ссылкой.
* **Кэш на мобильном интернете.** После любого редеплоя фронтенда пользователи с мобильного интернета иногда видели старую версию страницы со ссылками на уже не существующий JS бандл: сработало прозрачное кэширование у оператора связи. Решено явными заголовками `Cache-Control`: `no-store` для `index.html`, `immutable` с годовым сроком для хэшированных файлов сборки.
* **Лимит на размер загружаемого файла.** Дефолтный лимит nginx в 1 мегабайт не пропускал фото с телефона, добавлен `client_max_body_size 100m` на путь `/_matrix/`.

### Звонки из портала и доступ для внешних

Кнопка «Создать конференцию» в портале спрашивает у сотрудника название (вводит сам, не случайный набор символов) и переводит на встроенный через `JitsiMeetExternalAPI` звонок. Получение JWT идёт через тот же самый `/moderator/<комната>`, что и у обычной прямой ссылки: один и тот же путь авторизации работает для обоих входов.

Путь `/app/call/` намеренно не закрыт Keycloak гейтом, в отличие от остального `/app/`, чтобы по прямой ссылке на встречу могли зайти и внешние гости, а не только сотрудники. Для них просто не находится сессии Keycloak, и фронтенд подключается тем же анонимным гостевым способом, что работал бы и без портала вообще.

## WAF и мониторинг

Отдельным запросом от сетевой команды на сервер поставили WAF (продукт на технологии Wallarm). Особенность в том, что у сервиса один белый IP, а его медиа трафик идёт по UDP, который через типовой HTTP WAF всё равно не проходит, поэтому решили ставить агента прямо на сервер, а не заворачивать трафик через отдельные ноды.

Для установки пришлось делать точечное исключение из полного отсутствия исходящего интернета: открыли 443 порт наружу только на несколько доменов самого продукта. Режим работы выставлен в `monitoring`, а не `block`: агент только анализирует трафик и репортит в облако, ничего не блокирует. Осознанный выбор для первого включения на сервере с нестандартным трафиком (WebSocket сигналинг Jitsi, JWT в URL, долгий polling у Matrix): сначала посмотреть на ложные срабатывания, прежде чем включать реальную блокировку.

Отдельно для внешнего сервера мониторинга открыты по конкретному IP через UFW порты `node_exporter` и приёмника логов, точечными правилами, а не для всех подряд.

## Работа без интернета на сервере

Через всю статью проходит одно постоянное ограничение: у продуктивного сервера нет исходящего доступа в интернет вообще, ни к GitHub, ни к Docker Hub, ни к npm, ни даже к обычным репозиториям пакетов, кроме отдельно согласованных исключений вроде домена WAF провайдера.

Из-за этого весь нестандартный софт собирался или скачивался в отдельной песочнице с доступом в интернет и доставлялся на сервер архивом по scp:

* статическая сборка oauth2-proxy;
* статический бинарник Node.js, на котором крутятся jwt-minter, matrix-auth-bridge и portal-web;
* Docker образы для Synapse и Postgres тянулись бинарником `crane` в песочнице и заливались через `docker load`;
* собранный фронтенд портала (`npm run build` тоже в песочнице).

## Текущее состояние сервера

На момент последней сверки все компоненты подтверждены рабочими:

* все systemd сервисы (`oauth2-proxy`, `jwt-minter`, `matrix-auth-bridge`, `portal-web`, WAF агент, nginx) в статусе active;
* все Docker контейнеры (jicofo, prosody, jitsi web, JVB, Matrix Synapse, Postgres) подняты и работают;
* флаги `docker-jitsi-meet/.env` (`ENABLE_AUTH`, `AUTH_TYPE=jwt`, `ENABLE_GUESTS`, `JICOFO_ENABLE_REST`, `ENABLE_P2P=0`, `ENABLE_AUTO_OWNER=0`) соответствуют описанной здесь логике;
* конфигурация oauth2-proxy содержит оба апстрима, для `/moderator/` и для `/app/`, с общей сессией на весь домен;
* `nginx -t` проходит без ошибок, все ключевые location блоки (`/moderator/`, `/oauth2/`, публичные `/app/call/` и `/app/assets/`, закрытый `/app/`, `/_matrix/` с увеличенным лимитом тела запроса, regex гейт с проверками `jwt`, `guest_name` и `Sec-Fetch-Dest`) на месте;
* живые проверки эндпоинта jicofo и статуса модераторского шлюза отвечают штатно;
* настройки Synapse (изоляция от федерации, отключённая регистрация) соответствуют описанным решениям.

Из того, что осталось на будущее: полный сквозной тест всех четырёх сценариев доступа (гость к чужой встрече, гость создаёт новую, сотрудник создаёт, сотрудник заходит в чужую) стоит повторять вручную после каждой правки `.env` или nginx конфига, потому что часть логики (гонка при создании комнаты, обработка iframe) завязана на точное поведение браузера, которое трудно полностью покрыть автоматическими проверками с сервера.

## Что сделано из последних доработок

* Индикатор «идёт запись» для остальных участников при локальной записи звонка: включён штатный флаг Jitsi `config.localRecording.notifyAllParticipants`, до этого он был выключен по умолчанию и запись шла незаметно для собеседников.
* Водяной знак с логотипом: по итогам проверки в реальных звонках решили убрать его из интерфейса полностью, а не только во время конференции, как планировалось изначально. Сделано через CSS в `head.html`, без изменений в React коде Jitsi.
* Запись сразу в mp4 сознательно решили не делать: браузерный `MediaRecorder`, на котором построена локальная запись Jitsi, умеет только webm, а серверная запись через Jibri означала бы отдельный контейнер и решение вопроса хранения файлов, сочли избыточным на данном этапе.

## Пересборка фронтенда мессенджера

Статус прочтения сообщений в чате (счётчик «прочитано X из Y» с раскрывающимся списком в групповых чатах, галочки в личных), по образцу привычных мессенджеров, был исходным поводом для этой доработки. По пути выяснилось, что исходники фронтенда портала собирались во временной рабочей папке на отдельной машине с доступом в интернет (сам сервер `go.example.ru` без исходящего интернета, см. раздел про работу без сети выше), а на сервер заливался только готовый собранный бандл. Временную папку со сборки потеряли при перезагрузке машины, восстановить не удалось.

Решение: пересобрать фронтенд с нуля по детально задокументированному поведению (разделы выше), на этот раз с git с первого коммита. Исходники лежат прямо в этом репозитории, в папке `portal-web/`.

Все семь этапов пересборки завершены: каркас, переписка один на один, группы с вложениями и редактированием, реакции с ответами и опросами, звонки с модераторской логикой, тот самый статус прочтения, и наконец профиль с контактами и уведомлениями. На каждом этапе сборка и тесты проходили чисто, включая юнит-тесты для двух по-настоящему алгоритмических мест: подсчёта голосов в опросах и сравнения позиции событий в таймлайне для статуса прочтения. Перед реальным деплоем остаётся сквозной тест на живом Matrix-сервере, вся разработка до этого момента шла без него.

## Что лежит в этом репозитории

| Путь | Соответствует на сервере |
|---|---|
| `nginx/sites-available/go.example.ru.conf` | конфигурация основного домена |
| `nginx/conf.d/geo-internal.conf` | определение внутренних подсетей для geo директивы |
| `nginx/branding/` | статический брендинг (логотип, JSON с палитрой) |
| `nginx/nginx-static/external-stub.html` | заглушка для внешних посетителей на пустом корне домена |
| `oauth2-proxy/oauth2-proxy-go.cfg.example` | конфигурация OIDC шлюза (секреты заменены плейсхолдерами) |
| `jwt-minter/` | сервис выдачи JWT модератора |
| `matrix-auth-bridge/` | мост между Keycloak сессией и Matrix |
| `portal-web/server.mjs` | сервер раздачи фронтенда портала (без собранного бандла, он собирается отдельно) |
| `portal-web/src/`, `package.json`, `vite.config.ts` и т.д. | исходники фронтенда мессенджера, пересобираются с нуля, рабочая сборка ведётся отдельно на рабочей станции |
| `jitsi-meet-cfg/web/` | все переопределения интерфейса Jitsi |
| `docker-jitsi-meet/` | compose файл и пример переменных окружения |
| `matrix/` | compose файл Matrix стека и пример конфигурации Synapse |
| `systemd/` | юниты всех самописных сервисов |

Секретов в репозитории нет: все `*.env`, `*.cfg` и `homeserver.yaml` с реальными значениями заменены на файлы `*.example`, где чувствительные поля (секреты клиента OIDC, cookie secret, JWT секрет, административный токен Matrix, XMPP пароли, ключи подписи Synapse) помечены как `<REDACTED>`. Собранный фронтенд портала в репозиторий тоже не входит, поскольку это бинарный артефакт сборки, а не исходный код.
